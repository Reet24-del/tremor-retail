## How this was run (method)

1. **Development set, seeds 1000-1049.** First run: recall 99.0%, precision 98.6%. Failures were inspected by hand.
   One was a logic bug: an invoice line waiting for match confirmation was treated as a missing delivery, which
   created a fake stock discrepancy. Fixed so such stock signals are held as "needs data" (regression test added).
   No detection threshold was changed.
2. **Held-out set, seeds 2000-2049.** Never inspected before the fix. The numbers at the top of this page come from
   this set only.

## Why the remaining errors happen

- **Misses:** a planted cost jump of roughly 7-10% can fall under the robust z-score threshold when several other
  products in the same store drift 3-5%, because that widens what counts as normal.
- **False positives:** cheap items rounded up by one rupee (for example 22 to 23, +4.5%) with the selling price left
  flat. These are real but small leakages that the generator labelled as noise, so they are borderline.
- **Decoys not surfaced:** a bulk order that does not look off-cycle is simply not flagged at all. It is never
  escalated, but the evaluation counts the missing visible rejection.

## Limits of this test

- All stores use the same supplier invoice layout, so extraction accuracy here reflects the parser on that layout only.
- Product names come from one catalog with randomised invoice wording; real shops will have more variation.
- Metrics describe synthetic stores, not production accuracy.
